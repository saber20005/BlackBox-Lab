# خريطة مستودع BLACKBOX Lab

> المستودع **موقع JavaScript ثابت دون بناء bundler للواجهة**. بعض ملفات JavaScript في الجذر جزء من عناوين تُحمّل مباشرة من المتصفح؛ لا يجوز نقلها إلى `src` دون بناء أو تحديث روابطها واختبارات الاسترجاع.

## الهيكل بعد المرحلة الأولى

| المسار | الوظيفة | متطلبات الحفاظ |
| --- | --- | --- |
| `index.html` و`app.js` وملفات الواجهة `*.js` بالجذر | مدخل التطبيق الرئيسي ووحدات التدريب والحسابات | لا تغيّر عناوين الملفات المحملة مباشرة أو الاستيرادات دون فحص المتصفح |
| الصفحات `labs.html` و`mission-mode.html` و`portfolio.html` و`pro.html` وغيرها | روابط عامة قد يكون المستخدم احتفظ بها | تبقى في الجذر خلال هذه المرحلة |
| `assets/styles/` | **12 ملف CSS** مجمّعة بدل انتشارها في الجذر | حدثنا روابط الصفحات وتحميل CSS الديناميكي والاختبارات |
| `assets/modules/training/` و`assets/modules/diagnostics/` | وحدات JavaScript الداخلية: فهرس المختبرات والتشخيصات | لا تعطل روابط المداخل العامة؛ راجع الاستيرادات والاختبارات قبل النقل |
| `training-kit/` و`downloads/` | بيانات وأدوات التدريب الاصطناعية وملفات ZIP | لا تغير أسماء الملفات العامة دون تحديث الحزم والبصمات |
| `functions/` | Firebase Functions: التقييم الخادمي والعضويات | نشر منفصل عن Vercel، ولا تُرفع مفاتيح الإجابات |
| `firestore.rules` و`firebase.json` | صلاحيات وتكوين Firebase والمحاكيات | مسارات نشر ثابتة؛ لا تخلطها مع ملف Vercel |
| `local-agent/` | مساعد فحص VM المحلي وملفات Python | لا يُمنح صلاحيات إضافية بفعل تنظيم الملفات |
| `scripts/` | أدوات بناء الحزمة والفحوص والتدقيق | أدوات تطوير، وليست API للمستخدم |
| `tests/` | اختبارات Node وحالات التخزين والمزامنة | يجب أن تنجح قبل الدمج |
| `docs/` | توثيق التعليمات والأمان والتشغيل | [فهرس الوثائق](README.md) |
| `.github/workflows/` | اختبارات Node والمتصفح والمحاكي والوكيل | لا تعطّل الاختبارات لتجاوز مشكلة نقل |

## حدود يجب عدم اختراقها
- المفاتيح القديمة `blackbox-progress-v1` ومفاتيح التخزين المرتبطة بالحساب.
- المسارات `?view=...` و`?track=...` و`?stage=...` وصفحات `/labs.html` و`/portfolio.html` و`/pro.html`.
- `blackboxUsers/{uid}` وسجلات التقدم والمهارات وإيصالات CyberTrace الحالية.
- سجلات التقييم المُعدّة خادميًا لا تعني أن Firebase Functions قد نُشرت؛ يلزم نشر صريح واختبار أمني في بيئة الإنتاج.
- مستندات `socVerifiedRubrics` تتضمن مفاتيح خاصة ويجب ألّا تدخل GitHub أو حزمة الواجهة العامة.

## لماذا لم ننقل جميع ملفات JS؟
لأن `index.html` والصفحات الثانوية ووحدات التحميل الكسول تستورد أسماءها مباشرة من جذر الموقع. نقل ملف `app.js` أو `data.js` بلا مراجعة `import()` واختبارات المتصفح قد يكسر التدريبات والروابط، حتى لو نجح اختبار Node. نجمع الأصول المستقلة أولًا، ثم نقسم وحدات JS في طلبات دمج متدرجة مع توافق للمسارات.

## خطوة النقل الآمن
1. اعثر على كل استخدام في HTML و`import` و`import()` و`fetch` و`new URL` وملفات الاختبارات.
2. انقل مجموعة مترابطة صغيرة، وحدّث جميع المراجع في طلب دمج واحد.
3. شغّل فحوص `node scripts/check-repository-structure.mjs`، واختبارات `quality.yml` كاملة بما فيها المتصفح وقواعد Firestore وFunctions.
4. افحص الروابط المعلنة والصفحات على الهاتف بعد نشر Vercel؛ لا تفترض أن Vercel نشر قواعد Firebase.
5. لا تحذف الملفات التشخيصية مثل `appcheck-diagnostic.html` و`recaptcha-independent-diagnostic.html` و`ux-test.html`؛ ما زالت مستخدمة في نصوص وأدوات واختبارات.

## المرحلة التالية
تقسيم وحدات JavaScript في الجذر إلى مجالات `assets/modules/` أو بنية مصدر مبنية مع الإبقاء على روابط HTML. هذا تعديل مستقل أشد خطورة من تجميع ملفات CSS، ويحتاج اختبارات استخدام حقيقية للبيانات القديمة.
