# الحسابات والمزامنة الاختيارية

تظل الحسابات معطّلة في `account-config.js` إلى أن تُجهّز خدمة Firebase وتُفحص قواعد الوصول. التدريب وحفظ الضيف والنسخ الاحتياطية تعمل دون حساب. لا تضع مفاتيح Admin أو ملفات service account في المستودع أو المتصفح.

## تجهيز الخدمة

1. استخدم حساب Google المالك لمشروع Firebase المناسب، وأنشئ تطبيق Web إن لم يوجد. لا تُفعّل الفوترة تلقائيًا. يمكن تشغيل Authentication وFirestore ضمن الحصص المجانية المتاحة؛ تابع الاستخدام من لوحة الخدمة.
2. فعّل Email/Password في Authentication، وGoogle إذا أردت إتاحته، واضبط البريد الداعم المطلوب من الخدمة. أضف `blackboxlab.dev` وأي نطاق إنتاج آخر تستخدمه إلى Authorized domains. لا تضع نطاقات المعاينات غير المستخدمة ضمن القائمة.
3. أنشئ Cloud Firestore في الوضع الإنتاجي، ثم أضف القواعد الخاصة بالمسار `blackboxUsers/{uid}/state/progress`. إذا كان المشروع مشتركًا مع CyberTrace أو تطبيق آخر، اقرأ القواعد الموجودة وادمج المسار؛ لا تستبدلها بملف هذا المستودع كاملًا، لأن نهايته تمنع المسارات الأخرى.
4. انسخ إعداد تطبيق Web العام فقط إلى `account-config.js`، واضبط أعلام `providers` وفق المزوّدين المفعّلين فعليًا. اترك `emulators: null` في الإنتاج.
5. بعد نجاح الاختبارات وفحص النطاق والقواعد فعليًا، غيّر `enabled` إلى `true` وانشر النسخة. افحص إنشاء حساب والدخول والخروج والاستعادة والمزامنة بين متصفحين على النطاق الحقيقي قبل اعتبار الخدمة جاهزة.

نموذج الإعداد (القيم هنا أمثلة يجب استبدالها):

```js
export const accountConfig = Object.freeze({
  enabled: true,
  firebase: {
    apiKey: 'PUBLIC_WEB_API_KEY',
    authDomain: 'PROJECT_ID.firebaseapp.com',
    projectId: 'PROJECT_ID',
    appId: 'PUBLIC_WEB_APP_ID',
  },
  providers: Object.freeze({ email: true, google: true }),
  emulators: null,
});
```

## سلوك البيانات

بيانات الضيف باقية تحت `blackbox-progress-v1`. نقلها إلى الحساب إجراء صريح من نافذة الحساب، ويحتفظ الدمج بنصوص الملاحظات المختلفة. كل مستخدم يملك مستند تقدم خاصًا؛ تمنع قواعد Firestore الزائر والمستخدم الآخر من الوصول إليه.

تحتفظ التعديلات بنسخة محلية، وتُزامن بمعاملة تتحقق من رقم مراجعة المستند. يظهر تعارض إذا تغيّرت نسخة الحساب؛ يختار المستخدم الدمج أو النسخة التي يريدها. لا تعني عبارة «محفوظ في حسابك» نجاح الحفظ المحلي وحده. الخروج مع تغييرات معلّقة يحتاج مزامنتها أو اختيار الخروج دون مزامنة صراحةً، مع إمكانية تنزيل نسخة.

عند العثور على مسودات معلّقة من تبويبات هذا الحساب، تعرض نافذة الحساب تنزيلًا مستقلًا لكل مسودة بصيغة النسخة الاحتياطية المعتادة. يمكن استعادة أي ملف منها من صفحة النسخ والتقارير؛ يساعد ذلك على الاحتفاظ بالأصول قبل الدمج، خصوصًا إذا تجاوزت النتيجة حد المزامنة.

حد المزامنة 700,000 بايت لبيانات التقدم؛ حد النسخة الاحتياطية المحلية 5 MiB. البيانات التي تتجاوز حد المزامنة تبقى محليًا وتظهر رسالة واضحة؛ لا تُقتطع الملاحظات تلقائيًا. لا تُرسل كلمات المرور أو نصوص التقدم إلى التحليلات.

## الفحص المحلي

```sh
node --test --test-isolation=none tests/*.test.mjs
```

راجع [اختبارات قواعد Firestore](firestore-rules-tests.md) لتشغيل اختبارات الصلاحيات على المحاكي. لا تُعد اختبارات المحاكي دليلًا على تفعيل المزوّدين أو صحة قواعد مشروع الإنتاج؛ يُفحص كل منهما منفصلًا قبل التفعيل.

لاختبار المتصفح بمحاكيات Auth وFirestore، شغّل `firebase emulators:start --project demo-blackbox-account-tests --only auth,firestore` ثم خادم ملفات محليًا. استخدم إعدادًا محليًا يتضمن `emulators: { authURL: 'http://127.0.0.1:9199', firestoreHost: '127.0.0.1', firestorePort: 8180 }` ومشروع `demo-blackbox-account-tests`. لا تنشر هذا الإعداد؛ يتصل محوّل Firebase بالمحاكيات على مضيف محلي فقط.

يتوفر فحص متصفح قابل للتكرار في `scripts/test-accounts-browser.mjs`. يتطلب Playwright وChromium؛ يحقن إعداد مشروع المحاكي في طلب ملف الإعداد داخل المتصفح فقط، ويبقي ملف الإنتاج معطّلًا:

```sh
BLACKBOX_TEST_URL=http://127.0.0.1:4176/ \
BLACKBOX_PLAYWRIGHT_MODULE=/path/to/playwright/index.mjs \
BLACKBOX_CHROMIUM_PATH=/path/to/chromium \
node scripts/test-accounts-browser.mjs
```

عند تثبيت Playwright محليًا وتنزيل متصفحه يمكن حذف متغيري مساري المكتبة والمتصفح. يغطي الفحص إنشاء حساب، واستيراد الضيف، والمزامنة بين متصفحين، وتعارض الملاحظات، وعزل حسابين، والخروج، والعمل دون اتصال ثم إعادة المزامنة. يستخدم عناوين اختبار ضمن `example.test` ومحاكيات مشروع `demo-` فقط.
