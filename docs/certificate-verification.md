# Shared certificate verification registry — secure rollout plan

## Security truth

The live BLACKBOX certificate center currently prints three *self-reported* group-completion records based on a learner's manual stage confirmation. CyberTrace currently prints eight *self-reported* investigation-category records based on browser-saved results. Neither is a server-proctored qualification, and the existing PDFs do **not** become verified when this registry lands.

**Do not** migrate all existing PDFs into verified records. Keep legacy progress intact and clearly labelled as unverified.

## Phase 1: the shared authority (implemented in this PR, not yet deployed)

- Firestore `certificateRegistry/{certificateId}` is *server-only*, with explicit client read/write denial.
- `verifyIssuedCertificate` is a read-only GET Cloud Function using a random 128-bit lowercase hexadecimal ID. Its responses are `verified`, `revoked`, `not-found`, or `unavailable`.
- Only server-owned records with `proofType: 'server-assessment'`, `issuerAuthority: 'trusted-backend'`, and valid issuer/group/timestamps are eligible to be reported verified.
- The public response contains issuer, group, issue time, ID and revocation status. It omits the account UID, email, hidden answer keys, notes and other private evidence.
- Allowed browser origins are `blackboxlab.dev` and `cybertracelab.dev` (including `www`). CORS restrictions are not authentication: the endpoint is intentionally public and IDs must be unguessable.
- There is **no public issuance API**, no client write access, and no auto-approval based on completion flags, points or owner-writable Firestore receipts.
- Nothing in this phase prints QR codes or represents the old records as trusted.

## Phase 2: trustworthy evidence and actual issuance (NOT implemented)

1. Provision a distinct private server rubric and independently verified assessment(s) for every named group; do not publish expected answers in the client bundle.
2. Require a signed-in learner and a trusted server-side, replay-resistant assessment receipt for every requirement, with a versioned group rubric and threshold. Use server timestamps and transactional write-once/revocable issuance.
3. BLACKBOX uses Firebase project `black-box-lab`. CyberTrace uses `cybertrace-48ab0`. They are **different Auth issuers**: do not trust a CyberTrace UID, email, XP or browser receipt as identity or verified evidence in BLACKBOX. A separate signed, explicit account-linking exchange and trusted service-to-service verification is required. Link by proof of control, not matching emails.
4. Add issuance quotas, audit logs, duplicate issuance guards, cancellation/revocation policy, evidence retention and privacy/consent. Use encrypted/private evidence and least privilege. Never grant public Firestore access to the registry.
5. After end-to-end testing and owner approval, deploy Cloud Functions from the intended Firebase project with credentials controlled by the owner: `firebase deploy --only functions` from the BLACKBOX project. Vercel deployment alone **does not** deploy Firebase functions.
6. Add `/verify?id=<certificateId>` UX on both domains and render an ID/QR only for certificates actually present and active in the trusted registry. Display a clear unverified/unissued status on errors and legacy PDFs; never rely on a client-computed 'verified' indicator. Test mobile and desktop, cross-origin use, revocations, account switches, and rate limits.

## Registry schema (server-administrator controlled)

```js
{
  schemaVersion: 1, issuer: 'blackbox', groupId: 'network-foundations',
  groupTitle: 'الشبكات والاستطلاع', status: 'active', // or 'revoked'
  proofType: 'server-assessment', issuerAuthority: 'trusted-backend',
  issuedAt: serverTimestamp(),
  // Private records (uid, evidence reference and audit) stay inside Firestore.
}
```

Document IDs must be freshly generated by a CSPRNG with >=128 bits of randomness (32 lowercase hex digits). Never use an email, sequential ID, Firebase UID, stage key, or predictable time.

## Release gates

- Unit tests reject forged, invalid, leaked and revoked records.
- Firestore emulator denies clients all registry access, including owner accounts.
- Deploy the read-only function only after verifying Auth/project configuration and endpoint rate limiting.
- **No server-issued certificates** until per-group trustworthy assessment receipts and account-bridge verification exist. No fake badge, QR, serial number, certificate signature or accreditation claim.

## Public verification UI (separate gated PR)

A read-only public view is staged at `/verify.html?id=<32 lower-case hex>`. This is **not an issuance page**; a browser cannot create an ID or mark any self-reported training record as server-assessed. It accepts only server responses with matching ID, issuer, group and evidence type, differentiates valid, revoked, unknown and service-unavailable states, and never assumes network failure means counterfeit. No progress access, account login or database writes are required.

The page intentionally has no link from current legacy training PDFs and must not advertise true verified issuance until the Firebase Cloud Function is separately deployed, the service is tested, and independently evaluated group assessments are live. The production endpoint URL is `https://us-central1-black-box-lab.cloudfunctions.net/verifyIssuedCertificate` **only after** owner-controlled Firebase deployment; Vercel is unrelated to this function deployment.
